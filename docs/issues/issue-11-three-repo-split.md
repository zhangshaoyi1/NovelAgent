# 问题 #11：三个顶级目录应为「并列三仓库」而非单一嵌套 git

| 项 | 内容 |
|---|---|
| 分类 | 工程 / 仓库结构 |
| 严重度 | 中（影响协作、权限、备份粒度） |
| 状态 | 已解决（拆为 `agent/` / `项目文档/` / `小说/` 三个独立 git） |
| 关联文件 | `D:/project/NovelAgent/{agent,项目文档,小说}/.git`、根目录不再有 `.git` |
| 证据 | 用户明确要求「三个文件夹是并列的，不是包含的，三个都是并列的」「应该是三个 git，不是一个 git」；最终三仓库各自 clean |

## 1. 问题描述
最初把 `agent`（代码）、`项目文档`（中文文档）、`小说`（生成物）放在同一目录树下，并试图用一个 git 管理全部。用户纠正：三者是**并列的顶级目录，各自应是独立 git 仓库**，不应互相嵌套或共用一个仓库。

## 2. 现象 / 证据
- 用户在对话中两度纠正：①「代码和小说是并列的，不是包含的，三个文件都是并列的」；②「这三个应该是三个 git，而不是一个 git」。
- 重构后：`D:/project/NovelAgent/` 下三个目录各自有 `.git`，**根目录无 `.git`**；提交：`agent` `92c072b` / `项目文档` `a8f472d` / `小说` `f48d761`（后续 `agent` 又推到 gitcode）。

## 3. 根因
- 初始组织沿用「一个项目一个仓库」直觉，没区分三者性质不同：代码要开源 / 发版，文档要协作审阅，小说是产出物（可能含草稿、体积大）。
- 混在一个仓库会让：代码发版被迫带上小说大文件；小说草稿污染代码历史；权限无法分开。

## 4. 解决方案（当前）
- 在 `agent/`、`项目文档/`、`小说/` 各自 `git init` 并独立提交；删除根目录 `.git`。
- 代码仓库（`agent`）又进一步改为 **src 布局**（见 issue-06），并推送到 gitcode（见 issue-10）。
- `.workbuddy/`（WorkBuddy 自动化与记忆数据）保留在 `D:/project/NovelAgent/.workbuddy/`，不属于三仓库之一。

## 5. 影响
- 三者解耦：代码可独立发版 / 上云；文档可独立协作；小说产出物独立版本化（且未设远程，保留本地）。
- 代价：需要管理三个仓库的提交 / 推送（目前仅 `agent` 上了 gitcode；`项目文档`、`小说` 仍仅本地 git）。

## 6. 改进建议
- **明确各仓库远程策略**：若要把 `项目文档`、`小说` 也上云，需分别设远程（用户未要求，待确认）。
- **根目录加一个说明文件**（如 `D:/project/NovelAgent/README.md`）：讲清「这是三个并列仓库的合集，各自独立 git」，避免后人误建根级仓库。
- `.workbuddy/` 应加入各仓库 `.gitignore` 或保持在三者之外（当前已在三者之外，正确）。

## 7. 复现 / 验证
```bash
for d in agent 项目文档 小说; do echo "--- $d ---"; git -C "D:/project/NovelAgent/$d" log --oneline -1; done
# 根目录应无 .git
ls -la "D:/project/NovelAgent/" | grep -c "\.git"   # 期望 0（仅子目录内含 .git）
```

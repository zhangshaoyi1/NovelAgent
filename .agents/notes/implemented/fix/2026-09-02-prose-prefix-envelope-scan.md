# Agent Note: 纯文本散文前置 + 杂散括号的 JSON 信封定位加固

Status: implemented

## Problem

`_escape_control_in_strings`（2026-09-01）修好了「信封内 draft 字面换行」，
但 ch237/ch238 实证暴露另一失败模式：创作模型**先吐一段纯文本规划**（常含
ASCII 直引号、甚至杂散 `{`），随后才是合法 JSON 信封。

此时 `parse_llm_json` 的第 3/4 策略都只针对**首个** **`{`** 定位：

* 散文里的杂散 `{` 使策略 3（首 `{`..末 `}`）跨越散文到信封，区间整体非 JSON；

* 策略 4（首 `{` 括号配对）若散文的 `"` 使字符串状态错位，或杂散 `{` 的配对
  无法在文本内闭合，会落错起点 → 解析整体失败 → 触发的仍是「纯 JSON 重试」，
  重试期模型照旧先作文，陷入间歇性循环。

## Decision

在 `parse_llm_json` 末尾追加**策略 5**：逐 `{` 起点做「括号配对 + 候选级独立
转义 + `json.loads`」，取第一个成功解析的完整对象返回。

关键点：

* 不再只试首个 `{`，而是遍历所有可能的对象起点，规避散文前置的杂散括号；

* 每个候选在解析前**独立**再跑一次 `_escape_control_in_strings`——散文前缀里
  的杂散直引号若已使全局预转义错位、漏掉信封内真实换行，可在候选级兜回；

* 该策略是纯增量回退，不影响第 1\~4 策略在干净输入下的快速路径与既有测试。

## Alternatives considered

* 提高 `json_object`/`json_schema` 强约束——仍是「从生成端降概率」，无法根治。

* 按已知密钥（think/action/draft）定位信封——侵入 schema，通用性差。

* 全局预转义 + 首 `{` 单一候选——正是被证伪的现状，无法覆盖杂散括号。

## Consequences

* 散文前置 + 信封的混合输出现在能可靠定位到信封，不再间歇重试、白耗预算；

* 候选级转义使信封内真实换行在极端错位下也能正确还原；

* 首 `{` 候选若自身即可解析（如散文里恰好有个合法小子对象），按「先到先得」
  返回——绝大部分场景信封是外层首个可解析对象，影响可接受；

* 已加回归单测 `test_extract_json_prose_prefix_then_envelope`（phase0）。

# NovelAgent 系统架构文档

## 一、总体架构原则

### 1.1 高类聚低耦合

* **高类聚**：每个子包（模块）只负责一个明确的职责领域，内部功能高度相关

* **低耦合**：子包之间通过明确定义的接口通信，依赖关系单向、不循环

### 1.2 单向依赖原则

```
entry (cli/__main__.py)
    ↓
workflows/ (工作流编排)
    ↓
agents/ (多智能体团队)
    ↓
core/ 分层：
    ├── story/  quality/  (业务领域层)
    ├── engine/  registry/  infra/  (核心引擎层)
    ├── llm/  (LLM 基础设施)
    └── base/  (基础基础设施)
    ↓
client/ (LLM 客户端)
    ↓
base/ (异常、LLM 协议、工具函数、结构化输出、注册表基类)
```

**核心规则**：下层绝不依赖上层，禁止循环依赖。

### 1.3 新增/修改功能必须遵守的原则

1. **文件归属**：新功能必须放在对应职责的子包中，不得在 core/ 根目录创建文件
2. **依赖检查**：新引入的 import 不得产生循环依赖
3. **单向引用**：下层包不能 import 上层包的内容
4. **接口统一**：所有子包通过 `__init__.py` 导出公共接口，内部实现对外隐藏
5. **文档同步**：新功能需同步更新对应子包的 README.md
6. **Agent Note**：影响架构 / 依赖方向 / 跨包契约的**架构变更必须补充 Agent Note**
   （`agent/.agents/notes/{lifecycle}/{class}/yyyy-mm-dd-topic-title.md`，DeepSeek Harness
   风格：头部 `# Agent Note:` + `Status:`，正文 Problem/Decision/Alternatives considered/
   Consequences），与代码在同一变更中同步；实施前写 `proposed/`，交付后迁移 `implemented/`。

## 二、核心分层架构 (core/)

### 2.1 base/ — 基础基础设施层

**依赖**：仅标准库（+ pydantic）
**被依赖**：所有上层包
**职责**：异常定义、注册表基类、重试机制、结构化输出、LLM 协议层、纯工具函数
**文件划分**：

* `llm.py` — LLM 协议层（LLMError / LLMConfig / LLMResponse / LLMProvider 注册表 / register\_provider）

* `utils.py` — 纯工具函数（parse\_llm\_json / safe\_remove / chunk\_text，零外部依赖）

* `structured_output.py` — 结构化输出（pydantic\_to\_json\_schema / extract\_json / StructuredOutputError）

> 下沉说明（2026-08-29）：LLM 协议 / 工具函数 / 结构化输出原位于 client 与 core 层，
> 因 client 与 core/base 需要复用、而这两层不得依赖上层，统一下沉至 base，
> 落实「client 仅依赖 base」与「base 零外部依赖（除 pydantic）」。

### 2.2 engine/ — 核心引擎层

**依赖**：base/、client/
**被依赖**：workflows/、cli/、agents/、infra/、tools/
**职责**：状态机、Agent 循环、**工具契约**（tool\_contracts：Tool/ToolRegistry/@tool，实现见 tools/，engine 不依赖实现包）、命令路由、工作流编排、事件流、多 Agent 协作

### 2.3 story/ — 故事领域模型层

**依赖**：base/、client/
**被依赖**：workflows/、agents/、infra/
**职责**：设定管理、伏笔、关系网、章节、高潮曲线、爽点剧本、套路存储
**子包**：story/meta/ — 元设计（世界观 Schema、产品哲学、写作方法论）

### 2.4 quality/ — 质量保证层

**依赖**：base/、client/、story/
**被依赖**：workflows/、cli/、service/、agents/、tools/（懒加载）
**职责**：小说质量相关的护栏、一致性校验与冲突仲裁、质量评分与读者吸引力评分、反馈改写
**子包（按关注点拆分）**：

* `quality/guardrails/` — 内容与形式合规护栏、配置/指纹/全量去重扫描、架构门禁（含 confirmation）

* `quality/consistency/` — 章节一致性校验（consistency\_checker、从 infra/ 归位的 conflict\_service 冲突仲裁）

* `quality/scoring/` — 通用质量评分（quality\_checker 含 LLM 审查）与读者吸引力六维评分（reader\_appeal）

* `quality/rewrite/` — 基于反馈的章节重写（feedback\_rewriter）
  外部统一从 `agent.core.quality` 顶层导入，子包结构对调用方透明。

### 2.5 llm/ — LLM 基础设施

**依赖**：无（不依赖任何其他 core 子包，仅标准库 + 可选第三方）
**被依赖**：client/、rag/（经 embed\_fn 注入）、memory/
**职责**：模型路由、预算规划、文本嵌入提供方（embeddings：OpenAI 兼容 / Ollama / Qwen 本地，从 rag/ 归位）、Embedding 路由

### 2.6 registry/ — 扩展机制注册表

**依赖**：base/
**被依赖**：workflows/、cli/
**职责**：技能注册表、题材包注册表、题材合并

### 2.7 infra/ — 基础设施层

**依赖**：base/、client/、engine/（doctor 诊断状态机）、story/
**被依赖**：workflows/、cli/
**职责**：一键写书编排（compose，质量门禁经回调注入）、上下文加载、仪表盘、健康诊断、钩子分发
**注**：冲突仲裁已归位 quality/consistency/conflict\_service.py（消除 quality ↔ infra 循环依赖）

### 2.8 其他子包

| 子包                   | 职责                                                                                      |
| -------------------- | --------------------------------------------------------------------------------------- |
| `rag/`               | 检索增强生成（索引、检索、向量存储；embedding 能力经 llm/ 注入）                                                |
| `event_sourcing/`    | 事件溯源（事件总线、存储、恢复、事件化重试包装器）                                                               |
| `llmops/`            | LLM 运营（成本、追踪、评测）                                                                        |
| `anti_ai/`           | AI 味检测与压制                                                                               |
| `supervisor/`        | 长小说监督体系                                                                                 |
| `auto_orchestrator/` | 自动编排                                                                                    |
| `tools/`             | 工具实现层（内置工具、MCP 桥接；契约在 engine/tool\_contracts，依赖 engine/ + story/ + rag/ + quality/ 懒加载） |

## 三、上层模块

### 3.1 agents/ — 多智能体团队

| Agent            | 职责                             |
| ---------------- | ------------------------------ |
| `PlannerAgent`   | 架构师，产出 Master Plan             |
| `EditorAgent`    | 主编，一致性仲裁                       |
| `EvaluatorAgent` | 评测员，全书"不崩"终审                   |
| `WriterAgent`    | 自主写章 Agent（Writer + Critic 内联） |

### 3.2 workflows/ — 工作流

| 工作流              | 对应阶段 | 职责               |
| ---------------- | ---- | ---------------- |
| M1 Config        | 配置   | 项目初始化            |

| M14 Architecture | 架构   | 故事架构生成与确认        |

| M4 Character     | 角色   | 角色路线与关系网         |
| M5 Write Chapter | 写章   | 章节创作（含质量门禁）      |
| M6 Adjust        | 调整   | 路线/关系动态调整        |
| M8 Mode          | 模式   | 介入频率控制           |
| M10 Rollback     | 回滚   | 失败回退与续作恢复        |
| M11 Export       | 导出   | 导入导出             |
| M12 Audit        | 审计   | 内容审核与设定冲突        |
| M13 Foreshadow   | 伏笔   | 伏笔管理             |

| Agentic Write    | 写章   | 自主写章（Phase 1）    |
| Agentic Pipeline | 全流程  | 全流程自主编排（Phase 2） |

### 3.3 cli/ — 命令行接口

命令注册通过 `@command` 装饰器自动注册到 `CommandRouter`。

### 3.4 client/ — LLM 客户端

统一 LLM 调用入口，封装 provider 选择、结构化输出和 embedding 路由（通过 core/llm/embedding\_router 间接调用）。
**依赖**：仅 base/（通过 core/llm/ 间接依赖 rag/embeddings，不直接耦合）

### 3.5 service/ — 服务层

进程内服务接口，供 CLI 与 Web UI 共用。

### 3.6 web/ — Web UI（零构建工作台）

FastAPI 服务端渲染 + Jinja2 模板 + HTMX 局部刷新 + SSE，**不引入 Node 工具链**。

| 模块 | 职责 |
|---|---|
| `app.py` | 路由层：11 个页面路由 + 20 余个 JSON API；注册 `md` 模板过滤器（剥离 frontmatter 后渲染 markdown） |
| `state.py` | **项目状态的唯一读写门**：`get_project_state` / `read_project_file` / `write_project_file` / 阶段状态与复核 / 问答持久化。所有文件 I/O 经此收敛，含越权路径校验 |
| `runner.py` | `RunManager`：以子进程驱动 `python -m agent.cli <cmd> --dir <项目>`，合并 stdout/stderr 推 `log` 事件；每 0.4s 轮询 `.state/progress.json` 按 seq 增量推 `progress`；进程结束推 `done` |
| `qa_templates.py` | 各内容阶段的引导问题模板 |
| `templates/` | Jinja2 页面模板（base / home / project / guide_stage / writer / dashboard / files / file / team / graph / conflicts） |
| `static/` | `app.js`（运行控制台、SSE 消费、复核与问答面板、图谱交互）+ `style.css` |

**架构约束**

1. **不重写业务逻辑**：Web 端一律通过子进程调用 CLI（或直调既有 workflow 的只读方法），禁止在 `web/` 内实现第二套创作逻辑——保证网页能力与 CLI 永不漂移。
2. **门禁同源**：`app.py` 顶部 `import agent.cli.commands` 触发全部 `@command` 注册副作用，使 Web 的 `available_commands` 与 CLI 完全一致。
3. **降级不阻断**：LLM 调用失败、状态读取异常一律降级返回，不阻断页面渲染；SSE 之外保留 `GET /api/runs/{id}` 轮询兜底防假死。
4. **不阻塞事件循环**：长任务一律 `asyncio.create_task` 调度，页面路由保持同步快返回。
5. **交互命令不挂起**：子进程 `stdin=DEVNULL`，遗漏的交互式命令在 EOF 处快速失败。

**依赖方向**

```
web/ ──▶ cli.commands（命令元数据注册，副作用）
     ──▶ core.story.relation_manager（世界图谱）
     ──▶ core.story.meta.philosophy（首页文案）
     ──▶ workflows.m8_mode（自主度）/ m19_review_sync（复核同步）
     ──▶ agents.registry（Agent 阵容）
```

反向依赖禁止：`cli/` 与 `core/` 不得 import `web/`。

**新增命令如何同步进 Web**：在 `cli/commands/` 新增文件并使用 `@command(...)` 装饰器即可，Web 的「高级命令」区与项目工作台会自动出现该命令，无需改动 `web/`。

## 五、代码规范

### 5.1 文件组织

* 每个子包必须有 `__init__.py` 导出公共接口

* 每个子包必须有 `README.md` 说明职责和依赖

* 文件名使用小写蛇形（snake\_case）

* Agent 文件名使用短名称（如 `planner.py` 而非 `planner_agent.py`）

### 5.2 导入规范

* 优先使用绝对导入（`from agent.core.story.setting_manager import ...`）

* 避免循环导入：如果 A 导入 B，B 不能导入 A

* 延迟导入（lazy import）用于解决不可避免的循环依赖

### 5.3 架构合规

* 所有 Agent 必须继承 `base.Agent` 抽象基类

* 所有 LLM 调用必须通过 `client/LLMClient` 统一入口

* 使用 Registry/Provider/Consumer 模式进行动态加载
